For developers

Alto is a Python application using PySide6. The source is at github.com/altosaurus/alto.

This page is the quick reference: commands, tooling and the short recipes. Resources explains how the program works and the ideas underneath it (audio, notation, spaced repetition, styling, animation), with reading lists.

Layout

Folder

What is in it

alto/theory/

The music theory engine: spelled notes, intervals, scales and chords. Pure Python, no Qt.

alto/exercises/

The exercises, the Question and Exercise base classes, and registration of installed instrument packs.

alto/learning/

Profiles, the SQLite database, the scheduler and the statistics calculations. No Qt.

alto/ui/

The Qt widgets: main window, staff drawing, exercise screen, charts, settings and the database page.

alto/assets/

Bundled music fonts and instrument recordings.

tests/

The test suite.

The theory, exercise generation, and learning code can be tested without a display. The pack loader uses Qt’s image reader to check each supplied picture against its original dimensions. Plugin API

Running the tests

pip install -e ".[dev]"
pytest -n auto        # the whole suite, on every core at once
pytest tests/test_audio.py   # one file, in one process

-n auto (from pytest-xdist) runs the tests in one process per core, which takes the suite from minutes to under a minute. Leave it out when running a few tests, where starting the processes would take longer than the tests. sh scripts/run-tests.sh runs the suite the way the pre-push hook and GitHub do: everything but the performance budgets, on every core. The budgets time real operations, so they run in the Budgets workflow instead (see below). Set ALTO_TEST_WORKERS to use a different number of processes.

Two checks keep the suite fast as it grows. A test that takes longer than 8 seconds fails (TEST_TIME_LIMIT in tests/conftest.py) unless it is marked @pytest.mark.slow, for a thorough check that is worth the time. And tests/test_test_speed.py fails when a test file gains a fixed wait (QTest.qWait or time.sleep) outside tests marked motion or slow: let animations and feedback finish with motion.settle() instead, which takes no time (see the Animation guide). When a file loses a wait, lower its number in that test’s BASELINE.

The tests that touch widgets run with Qt’s offscreen platform, so no display is needed.

The tests never read or change your own settings, profile or history. tests/conftest.py points them at a throwaway folder, closes every window and database a test leaves open, and turns the sound off. Coverage measures executable statements under alto/. The pre-push hook and the pytest job that collects coverage require tests to execute every added or modified statement in that package. The Codecov project percentage tracks historical gaps.

For code pull requests and pushes to main, the oldest Python version in the pytest matrix (currently 3.11) runs the suite with coverage and checks the patch. Download the pytest-coverage artifact from the Tests run to inspect coverage.xml. The Codecov workflow reads that same artifact. To measure coverage locally:

sh scripts/run-tests.sh --patch-coverage

Which checks run for which change

The pre-push hook runs the full pytest suite once and checks the resulting coverage against the branch diff from origin/main. Fetch the target branch first and set ALTO_COVERAGE_BASE when targeting another branch. On pull requests, GitHub selects pytest and coverage using the changes since the branch diverged from its base.

Ruff and Pyright run on pull requests that change Python source, type stubs, or inputs to the respective tool. For example, a Ruff configuration change runs Ruff, a change to scripts/typecheck.sh runs Pyright, and a change to pyproject.toml runs both. The Docs check builds a Sphinx preview for every pull request targeting main.

Pushes to main run the full suite on every supported Python version, along with Ruff, Pyright, and coverage. A new push to a pull request cancels its previous run.

Keeping Alto fast

Three things watch how fast Alto is, each for a different kind of slowdown. The operations they time are in benchmarks/operations.py: opening every page (and going between a lesson and an exercise), asking and answering a question, painting each screen, drawing the circle of fifths at new sizes, and reading and writing the data of a profile with a year of practice behind it.

  • Budgets, after each merge. tests/test_performance.py (marked perf) fails when an operation takes longer than its budget in benchmarks/budgets.py. A budget is four or five times what the operation takes on a development machine, so that a slow build machine does not fail a test but a change that makes something many times slower does. The first use of something in a new process (starting the app, the first look at a page, the circle at sizes not used before) is measured in a process of its own, because Qt makes fonts and layouts on first use and later runs hide that cost. The budgets time real operations, so they are left out of the pull request’s tests, where other test processes share the cores. The Budgets workflow (.github/workflows/budgets.yml) runs them on a machine of their own after each merge into main that touches the app, the benchmarks or the budgets, and by hand. A missed budget opens an issue labeled performance, or adds the run to the one that is open, and does not fail the run. Run them yourself with pytest -m perf.

  • A history, from release to release. benchmarks/suite.py is an ASV suite, and the Performance workflow (.github/workflows/performance.yml) measures main daily at 09:37 UTC and keeps the results on the branch asv-results. When the historical comparison flags a slowdown above 30%, the workflow measures the flagged operations again on the previous release and the candidate, using the same runner, benchmark suite, and Python environment. The run summary shows which slowdowns reproduced. Only confirmed slowdowns open or update a performance issue. The graphs keep the original full-suite measurements.

  • First visits. The first time a page shows text with ♯, ♭ or ♮ in a new size, Qt spends about 40 ms looking for a font that has the signs, because the interface font does not. alto/ui/warmup.py does that once for each size the interface uses, and loads the music font, a step at a time while the app is idle after it opens, so the first visit to a page is nearly as quick as the second. A new style sheet size belongs in its SIZES.

  • By hand, before a release. The run takes a minute or two, and the feel of animations on a real screen is not something a test can judge, so look at the lesson, the circle of fifths and the statistics page on a real display as well.

python -m benchmarks.survey        # every operation once, slowest first, in milliseconds
python -m benchmarks.operations page:lesson --profile   # where the time goes in one operation, the first time
pytest -m perf                     # the budgets
asv run -E existing:$(which python) --set-commit-hash $(git rev-parse HEAD)   # record this commit
asv compare v0.0.0 HEAD            # what changed since a release, once both have been recorded

When an operation is made faster or slower on purpose, change its budget in the same commit. A new page or exercise needs a line in benchmarks/budgets.py (a prefix such as page: covers it) and, if it is a new kind of operation, an entry in benchmarks/operations.py; the tests fail until it has a budget, so nothing goes unwatched. The first release to be measured is the one that has benchmarks/. To record a release baseline, run the Performance workflow by hand with ref set to its tag.

Type checking

Pyright checks the types of alto, tests and scripts, in basic mode, as if for Python 3.11:

sh scripts/typecheck.sh

It must report no errors. It runs on every pull request (.github/workflows/pyright.yml) and before each push. Two things to know when writing Qt code:

  • Write Qt enums in their full form, such as Qt.AlignmentFlag.AlignLeft, not the short Qt.AlignLeft. The short form works when the program runs, but Pyright cannot see it.

  • Qt functions that may return nothing (layout(), widget(), QApplication.instance()) have to be checked for None before use, with an if or an assert.

If Pyright is wrong about one line, silence just that line with # pyright: ignore[ruleName] and a short reason.

Running your copy apart from the installed one

Alto’s history and settings are kept by name, so a clone run with python -m alto shares them with an installed Alto. To keep them apart, run the clone with sh scripts/dev.sh. It sets ALTO_HOME to ~/.alto-dev (or to a folder you choose), where the clone has its own database and settings. The first run also adds “Alto (dev)” to the application menu, with the clone’s icon, so the dock shows the development copy on its own and not grouped with the installed one. See Database.

Pre-commit

A pre-commit configuration runs the checks automatically before each commit. Set it up once:

pip install -e ".[dev]"
pre-commit install

It then trims trailing whitespace, makes sure files end with a newline, checks YAML and TOML files, refuses very large files (the bundled recordings and fonts are exempt) and runs Ruff, applying its safe fixes. If a hook changes a file, the commit stops so you can review the change, then commit again.

On push, the hooks run the test suite, Pyright, and Pylint’s duplicate-code check (R0801). Pylint compares all modules in alto/ so it can find matches in unchanged files. A failure in any of these checks stops the push. Run the duplicate check alone with pre-commit run pylint-duplicates --hook-stage pre-push --all-files, the commit checks with pre-commit run --all-files, the push checks with pre-commit run --all-files --hook-stage pre-push, and update the pinned hook versions with pre-commit autoupdate.

Merged local branches

Run pre-commit install again in an existing clone to install the post-merge hook. When a merge or fast-forward pull updates your checked-out main, the hook deletes local branches whose tips are in both main and origin/main. Each deletion prints the branch name and its previous commit. Branches with new local commits or commits incorporated only by a squash merge stay available for review.

The hook skips every branch checked out in a worktree and always keeps main, gh-pages, and asv-results. To keep another long-running branch in this clone, add its exact name before pulling. Repeat the command for each branch you want to keep.

git config --local --add alto.keepBranch gd_dev
sh scripts/prune-branches.sh --dry-run

The preview refreshes origin and lists eligible local branches. The automatic hook uses the references already in your clone and only deletes local branches.

Linting

Alto uses Ruff for linting and formatting. It is installed with the dev extra and configured in pyproject.toml. Ruff checks code at 79 characters and docstrings and standalone comments at 72 characters throughout the repository. Docstring summaries can wrap or start on their own line.

ruff format alto tests scripts        # format the code
ruff check --fix alto tests scripts   # report problems and apply the safe fixes

Run them in that order. Anything that does not fit on a line, whether a list, a dictionary, a call or a signature, is put one element per line with a trailing comma, and a trailing comma you write yourself keeps a short one exploded. The ruff-format pre-commit hook does this on every commit. Ruff warns that the trailing-comma rule can conflict with the formatter. Run in this order, it does not: the formatter leaves out a comma after a lone long argument, the check adds it, and the formatter keeps it.

Imports follow these rules:

  • Absolute only. from alto.ui.store import store, never from .store import store (TID252).

  • At the top of the file. None inside a function (PLC0415), except in the >>> examples of a docstring, which have to import what they use. Two modules that need each other do not import each other: notation.py and keyboard_styles.py call hooks that staff.py and keyboard.py register with on_redraw. The conftest.py files set the settings folders before importing anything from Alto, so their imports are marked # noqa: E402.

  • One name per line when a from import has two or more names, in parentheses with a trailing comma. Ruff cannot enforce this, but it keeps an import you have already written that way.

  • Sorted like isort (I): the standard library, then third-party packages (PySide6, numpy, pytest), then alto as its own section (known-first-party), each section sorted alphabetically.

PyCharm

The code is kept free of PyCharm warnings as well as Ruff and Pyright errors. PyCharm’s settings live in .idea/, which is not in the repository, so a fresh clone needs the three changes below. Without them PyCharm shows many warnings that are not real problems.

1. Use a project inspection profile that ignores the alto imports. PyCharm analyses the >>> examples in docstrings, which is useful, but it resolves alto.exercises and the like only when the file itself imports them, so every example that imports from another package gets a false “Cannot find reference” warning.

  • Settings, Editor, Inspections: choose the Project Default profile (the one saved in the project, not the IDE one).

  • Under Python, Unresolved references, add these to Ignore references: alto.exercises.*, alto.learning.*, alto.theory.*, alto.ui.*, alto.audio.* and alto.__main__.

The result is this in .idea/inspectionProfiles/Project_Default.xml, with USE_PROJECT_PROFILE set to true in profiles_settings.xml next to it:

<inspection_tool class="PyUnresolvedReferencesInspection" enabled="true" level="WARNING" enabled_by_default="true">
  <option name="ignoredIdentifiers">
    <list>
      <option value="alto.exercises.*" />
      <option value="alto.learning.*" />
      <option value="alto.theory.*" />
      <option value="alto.ui.*" />
      <option value="alto.audio.*" />
      <option value="alto.__main__" />
    </list>
  </option>
</inspection_tool>

Names that really are unresolved are still reported, in code and in examples.

2. Add a database connection, so the SQL in alto/learning/database.py is checked. Without one, PyCharm warns about every SQL string.

  1. Make a file with the real schema, which Database creates when it opens a new file:

    python -c "from alto.learning import Database; Database('.idea/alto-schema.db').close()"

    Delete the file and run this again whenever the schema in database.py changes.

  2. In the Database tool window, add a SQLite data source named alto (schema) for that file (jdbc:sqlite:<path to the clone>/.idea/alto-schema.db).

  3. In Settings, Languages & Frameworks, SQL Dialects, set the Project SQL Dialect to SQLite (.idea/sqldialects.xml).

3. Leave “Analyze Python code in docstrings” switched on. The examples are real code, so PyCharm should keep checking them. A few habits keep them quiet:

  • Name example variables so they do not shadow a parameter or a module-level name; a trailing underscore is fine (database_, cfg_).

  • Where PyCharm cannot tell a value is not None, or the example deliberately uses a private member, put a comment line before that statement: >>> # noinspection PyUnresolvedReferences or >>> # noinspection PyProtectedMember. It covers only the next statement.

In code, suppress a false positive narrowly, with # noinspection <Inspection> on the line above the statement or the function, and say why when it is not obvious. A few things that are not obvious:

  • PyUnusedLocal is not honored for the parameters of a fake that has to match what it replaces; delete them explicitly (del volume, kwargs) instead.

  • Read saved text with text_value in alto/ui/store.py, not str(settings.value(...)), which PyCharm flags and Pyright needs.

  • Declare every attribute in __init__, not in the method that first sets it.

Designing lessons and exercises

A lesson teaches a musical idea that a learner can apply in several situations. An exercise gives repeated practice in one specific technique. In an identification exercise, the learner reads or hears an example and names what it is. In a construction exercise, the learner starts with a specification and supplies the notes or symbols that satisfy it.

Plan the relationship by learning goal. One lesson can prepare a learner for several exercises, and an exercise can reinforce ideas introduced in several lessons. Reuse an existing lesson when it already explains the idea a new exercise depends on.

An instrument plugin follows the same guidance for the lessons in its manifest, which Alto appends to alto.lessons.LESSONS with register_lesson when the plugin loads. Order the lesson tiles by prerequisite in alto.lessons.LESSONS. Start with a lesson that assumes no music theory knowledge. When adding a lesson, place it after the ideas it uses and before lessons that build on it.

  1. Choose the lesson outcome. Write one sentence describing what a first-time learner should understand by the end. Use that sentence to decide which examples belong and where the lesson should stop.

  2. Map the practice. For each related exercise, describe what the learner is given, what they do, and what makes the answer correct. Check the exercise catalog for a match before proposing a new drill.

  3. Check the vocabulary in teaching order. Read the lesson as a learner who has completed only the preceding lessons. For each musical term, find where its meaning was taught. If it is new, give a plain-language definition where the learner first needs it, before a diagram or question asks them to use it. A mention in a title or a glossary entry alone does not teach the term. For example, introduce the tonic as the note that feels like home, then ask the learner to find it. Repeat this check when reordering lessons.

  4. Build a short guided sequence. Introduce the idea with an example the learner can read or hear. When the concept is visual, consider annotating the first example to show where to look. On a keyboard, bracket the pair of black keys and label the neighboring C. On a staff, an arrow from “notehead” to the oval shows which part of the note to read. Then change one feature and ask the learner to predict or explain the result. Give feedback that points back to the example. Use the closing step to name the skills the learner can practice next. Choose the primary practice target with Lesson.exercise and list additional practice targets in Lesson.related_exercises.

  5. Time a first pass. Aim for 20 minutes or less, including reading, listening, guided questions, and time to use a hint. Count independent exercise practice separately. If the lesson runs long, move repeated trials into an exercise or split off a concept that has its own learning outcome.

Engraving lesson examples

Let the music determine the width of a lesson example. Measure spacing in staff spaces, where one space is the distance between the centers of adjacent staff lines. The values below are starting points for Alto. Measure horizontal gaps between the visible edges of the symbols, except where the table specifies notehead centers.

Where

Starting spacing

Clef to key signature

Leave 1 staff space before the first sharp or flat and ¼ space between successive signature marks.

Key signature to first note

Leave 1½ spaces before the notehead or its local accidental. With an empty signature, measure directly from the clef.

Local accidental to notehead

Leave ¼ space so the sign reads with its note. Stagger accidentals in a chord as needed to clear other signs, notes, and ledger lines.

Notes in a phrase

Start equal quarter notes 3½ spaces apart, measured from center to center. Give longer values more room and shorter values less. Allow clearance for flags, dots, and accidentals. Keep simultaneous pitches at the same rhythmic position.

End of a short staff

End the lines about 2 spaces past the last symbol, including when the example shows only a key signature.

Anchor short examples at the left. When the pane widens, let the extra room fall beyond the staff. When a longer phrase needs another line, wrap at a musical boundary and repeat the clef and key signature. For paired examples, align the left edges and clefs, keep the staff size consistent, and align corresponding beats when comparing phrases. Size the white box to the wider of the music and its caption, with a small margin around both. Once the example fits on one line, keep the box at that width as the pane grows. Let long captions wrap below the staff in a narrow pane. Allow enough height for the clef, accidentals, ledger lines, and every line of the caption.

Group related staves and their playback button in one bordered panel. Arrange the staves in reading order across the panel, with a vertical divider between neighbors on the same row. Use continuous white notation paper all the way to the panel border, including between staves and behind the playback button beneath the music. Use the theme’s light button colors on that paper. At a lesson content width of 760 pixels or more, align the top of the panel with the top of the explanation. Below that width, place the panel after the opening paragraph and before the remaining text and question. Keep paired staves together whenever both fit and wrap them when necessary.

Put each guided question in the Knowledge check callout. Keep its prompt, choices, hints, explanation, and retry control together. Let answer buttons wrap in reading order when space is tight.

Use StaffPlayback for a playable staff example. Its callback identifies each onset by position, so repeated notes light in reading order and a chord lights together. When two diagrams show the same sounding note, highlight both. Clear the playback highlight at the end and when changing examples.

Lesson diagrams use StaffWidget(lesson_layout=True) in alto/ui/lesson.py and the lesson’s scale explorer. The renderer measures the selected notation font and keeps each chord together when wrapping. In the scale explorer, a step label followed by an arrow leads to the first pitch on the next line.

To check a layout change, view an F natural in G major, a three-flat bass-clef signature on its own, and a short run of quarter notes in both narrow and wide panes. The natural should read with the F, the flats should read as one group, and widening the pane should preserve the distance between the quarter notes. Also try a single note with a caption wider than its staff. Narrow the pane until the caption wraps, then widen it again. The last word should stay visible throughout, and the white box should stop growing once the caption fits on one line.

Reviewing the lesson sequence for gaps

Review the affected stretch whenever a lesson is added, moved, or substantially revised. Every few lesson changes, walk the full sequence in the order given by alto.lessons.LESSONS. Start with an absolute beginner and carry forward what each lesson actually teaches. An optional exercise or glossary lookup can reinforce a skill, but a learner can reach the next tile without doing either.

  1. Work through the next lesson’s examples and questions. For each, finish the sentence “To do this, I already need to be able to …” Include reading the diagram, hearing a difference, and interpreting the answer choices.

  2. For each prerequisite, record the earlier lesson and step that teaches it, or the worked example in the current lesson before its first use. Distinguish seeing a definition, following a demonstration, and using the idea on a fresh example. Match the evidence to what the question actually asks the learner to do.

  3. Try one fresh example with the same demands. For instance, after a learner reads a note just above a known line, ask them to read one just below it. When possible, watch a first-time learner try it before giving a hint. Record where their reasoning stops. A walkthrough by the author and an observed learner result are different evidence.

  4. Flag a blocking gap when an essential action requires knowledge the sequence has yet to teach. Flag a practice gap when the explanation exists but the jump to independent use needs a smaller example. Record one row per finding. Keep a row open until someone retries the original task using the revised sequence.

Example lesson plan for scales

A lesson on Scales could ask, “How can the same major-scale pattern start on two different notes?” Have the learner play C major, locate the half steps, then start on G and decide whether F or F♯ preserves the pattern. Close by playing the G scale they predicted. An illustrative first pass allows four minutes for C major, six for the guided G major example, and three for the comparison and recap.

Adding an instrument

  1. Put its recordings in alto/assets/samples/<key>/, one mono WAV per note, named by MIDI note number (for example 60.wav for middle C). Every semitone is best. Where a note has no recording, Alto shifts the nearest one.

Versions of the docs

The docs exist in one copy for each release and one for the development version, and a dropdown in the top bar switches between them. A page of an old release says so in a banner, and links to the same page in the latest one.

/alto/dev/        the development version, rebuilt when docs, API source, or build inputs change on main
/alto/v0.1.0/     one folder for each release, built once when its tag is pushed and not changed after that
/alto/            the newest stable release (redirects to dev until there is a release) and shared files
/alto/latest/     compatibility redirects to the same pages at /alto/

The Docs workflow (.github/workflows/docs.yml) builds them with Sphinx and keeps the result on the branch gh-pages, which GitHub Pages serves. scripts/docs_site.py installs the stable build at the root without replacing the version folders and writes versions.json and the compatibility redirects. The files that belong to the whole site and not to one version are in docs/site-root/. One of them, version-switcher.js, fills the dropdown from versions.json at run time, so a release made years ago still offers the newest versions, and a fix to the dropdown reaches all of them. The dev entry shows the short Git hash recorded when those docs were built.

Search engines are told to prefer the latest version: every page has a canonical address under /alto/, dev is noindex, and only the stable build is in the root sitemap.

A release archive keeps the HTML from its first publication. To publish a missing Sphinx release, run the Docs workflow with ref set to the tag. The build reads the guides, Python source, and locked dependencies from that tag. A prerelease gets a version folder. The newest published stable release also gets a build at the site root. Earlier releases retain their original renderer’s output and read the current version list and plugin registry from the shared site root.

Switching a copy of the repository to this, once: after the first run has created the gh-pages branch, set Settings, Pages, Source to “Deploy from a branch”, gh-pages, / (root). Until then GitHub builds a single copy from main:/docs as before. Do this soon after merging, because the one copy no longer has robots.txt, llms.txt or the Search Console file, which now live in docs/site-root/.

A merge into Alto’s main rebuilds the docs, and a change to a tutorial reaches the site at the next build, so run the Docs workflow by hand after you push a tutorial. The pictures in each tutorial are made by that repository’s scripts/screenshots.py. The plugin tests keep only the manifest of each example pack in tests/packs/ (and the viola’s animation), and make its recordings, photographs and icons when they run (tests/pack_fixtures.py), because the plugin’s author provides the real ones. They also read the tutorial pages when they have been brought in.

Keeping the docs and screenshots current

The current app screenshots in docs/assets/img/ come in light and dark pairs. Regenerate them with scripts/screenshots.py:

.venv/bin/python scripts/screenshots.py                    # every picture, both themes
.venv/bin/python scripts/screenshots.py --only home stats  # just these
.venv/bin/python scripts/screenshots.py --out /tmp/shots   # somewhere else, to look before replacing

For a release, start with .venv/bin/python scripts/screenshots.py --review /tmp/alto-shot-review using an empty directory. The script compares decoded pixels with the checked-in PNGs. It writes new or resized captures and those where at least 0.5% of pixels differ by more than 16 levels in any 8-bit color channel. Each line reports the changed percentage. Review the candidates beside the existing screenshots and copy only those that show a change readers need to see. A different sample question, chart value, or row of practice data can cross the threshold without changing the instructions. For a small important detail, such as the version in Settings, use --only settings-updates --force to capture it regardless of the percentage. An empty --out folder gives you every capture for inspection.

The sample profile uses fixed random seeds, a fixed date, and UTC. Each theme gets its own temporary settings folder. The script needs a display or QT_QPA_PLATFORM=offscreen. Fonts render slightly differently on each machine, so regenerate on the machine you normally use and look at the pictures before committing them. To add a picture, include it in a docs page with shot.html, and add its name to SHOTS in the script. tests/test_docs.py checks that both match and that both themes exist.

The Developer guide uses component-shot.html for clickable screenshots. Give the include the capture’s width and height. In docs/_data/launch_components.json, each region records its label, class, destination, and rectangle (left, top, width, height as percentages of the image). The screenshot and its numbered key share those destinations. After a recapture, check that each region still covers its component in both themes.

The pre-push hook runs scripts/check-docs.sh, which warns when the interface (alto/ui) has changed since the pictures were last updated. It only warns; set ALTO_DOCS_STRICT=1 to make it fail.

The API reference

The API reference is built from the Python files under alto/. Sphinx AutoAPI reads the source without starting Qt. Each module links to a page for each public class and module-level function. Class pages include the constructor, methods, and links to the Python source.

Edit the Python signature or docstring, then rebuild the local preview to see the change. The build generates the reference, walkthrough line numbers, and search index together. Commit the source edits. The PR preview shows their rendered pages.

Changelog and releases

CHANGELOG.md lists what changed for the people who use Alto, newest first, in the Keep a Changelog layout. A change a user would notice (a new exercise, a changed menu, a fixed bug) adds a line under Unreleased in the same pull request. Internal tidying does not need one.

Pre-release checklist

  1. Choose the version. Alto uses semantic versioning: a new feature raises the middle number, a fix raises the last.

  2. In CHANGELOG.md, rename Unreleased to the version with today’s date (## [0.1.0] - 2026-12-01), add a new empty Unreleased above it, and update the two links at the bottom. The docs build reads the release notes from this changelog.

  3. Set the same version in pyproject.toml. tests/test_changelog.py fails if the changelog has no notes for it.

  4. Check that every user-facing feature in the release has a guide entry explaining where to find it and how to use it. Compare the changes since the previous release tag with the changelog to catch any omissions. For each new or changed feature, follow the documented steps in the release candidate and add or correct instructions in the release PR.

  5. With the release candidate installed in .venv, run the screenshot comparison for both themes. Review the changed images against their captions and alt text, including small release-specific details such as the displayed version. Exclude the UI style guide and its versioned screenshots in docs/assets/ui-reference/ from this check. Update that baseline only for an explicitly requested visual change. For screenshots using component-shot.html, check that the image dimensions match the captures and each clickable region covers its component. Run sh scripts/run-tests.sh tests/test_docs.py tests/test_docs_site.py tests/test_guide_docs.py and include the updated images and any caption or region corrections in the release PR. Confirm that the upgrade fixture comes from the previous stable desktop release. The Linux package job opens it, answers its due card, and reopens it.

  6. After merging the release PR, run Release manually on the versioned main commit. Download the release-candidate artifact from that run. Check its ZIP SHA-256 against the run summary, unpack it, and run sha256sum --strict --check SHA256SUMS inside. Confirm SOURCE-COMMIT and review the three *-packages.json inventories. Complete the license compliance check using the included Linux tarball, signed Windows installer, stapled macOS DMG, and source archives. Record the run, artifact ID, ZIP checksum, and review results in the release PR.

  7. Copy the entire Candidate: <artifact-id> <zip-sha256> annotation from the reviewed run summary. Tag the commit recorded in SOURCE-COMMIT. For example, substitute the reviewed values in git tag -a v0.1.0 <source-commit> -m 'Candidate: <artifact-id> <zip-sha256>' and run git push origin v0.1.0. The tag workflow verifies the candidate and compares every uploaded asset’s SHA-256 before making the release public. If the artifact expires before tagging, build and review a new candidate.

Publish a release as a normal release, not a pre-release: the update check asks GitHub for the latest release, which leaves pre-releases out, and compares version numbers (0.10.0 is newer than 0.9.0), so a tag must be plain numbers such as v0.1.0.

python scripts/changelog_section.py 0.1.0 prints the notes of one version, which is what a GitHub release shows. alto --version prints the version of the copy you run.

License compliance

  • Bundled software and assets. Unpack the Linux tarball, install the Windows candidate, and mount the final stapled Mac DMG. On each platform, inventory the interpreter, frozen Python packages, embedded native code, Qt plugins and system libraries. Compare the contents with the exclusions in packaging/alto.spec. Check redistribution terms for each component and for the fonts, recordings, score excerpts, icons and vendored documentation assets. Confirm that Alto’s MIT license and the applicable third-party licenses and credits accompany the copies users receive, including the versioned documentation.

  • Installed notices. Compare the inventory with THIRD_PARTY_NOTICES.md and the installed licenses/README.txt. Check the notice texts against the exact upstream versions, including incorporated code such as CPython’s HACL*. Verify each SHA-256 in licenses/notices.json and resolve every license-file reference in licenses/Qt/upstream-notices.zip.

  • Corresponding source. Match the Qt and Qt for Python source downloads to the versions and hashes in each installation. Verify that the Qt libraries and PySide6 and Shiboken bindings can be replaced and that Alto’s self-test still passes. Check the bundled Linux libraries against their package copyrights and verify the required Ubuntu source packages and file hashes in the companion archive. Verify the certifi source download and compare its CA bundle with the installed copy.

  • Mac bundle. Check the signed resources in Alto.app/Contents/Resources, the Mach-O dependencies, and the source companions distributed with the disk image. Run the documented Qt and binding replacement procedure on a writable copy, verify the modified behavior, and exercise WAV playback. Validate the stapled ticket and Gatekeeper assessment on the original disk image and app.

  • Windows upgrade terms. Upgrade from the previous release with no recorded acceptance of the current Microsoft terms. Exercise both choices through Alto’s updater. Declining must preserve the old installation, and accepting must complete the upgrade and record acceptance.

  • Release evidence. Keep the review tied to the candidate ZIP identified by the annotated tag. The signed SHA256SUMS covers the desktop downloads, source companions, source commit, and version inventories.

Building the Linux download

sh scripts/build-linux.sh                       # dist/alto-<version>-linux-<architecture>.tar.gz, and its .sha256 file
PYTHON=/path/to/python3.13 sh scripts/build-linux.sh

The script uses uv to install the locked package extra in a clean environment under .package-build/, freezes Alto with packaging/alto.spec, and packs the result with packaging/linux/install.sh, a README, the license and the third-party notices. Nothing is installed on your computer. Before it packs anything it checks that the frozen program says Alto <version> and that it opens its window (under Qt’s offscreen platform, with its own data folder, so a real profile is never touched).

The download is the program folder, which carries its own Python and Qt, so users need no Python. install.sh install copies it to ~/.local/opt/alto, links ~/.local/bin/alto and adds the menu entry; uninstall removes those and keeps the user’s data, and uninstall --purge deletes that too. tests/test_linux_install.py runs the real script in a scratch home.

Two things to know when building a release:

  • Build on an old Linux. The frozen program needs at least the C library of the system it was built on, so the release workflow builds on Ubuntu 22.04, and a build made on a newer system will not start on older ones.

  • System libraries come from the build machine. PyInstaller copies the libraries Qt needs from the system it runs on (including GTK, glib and libstdc++), apart from a short list it leaves out (graphics drivers, libxcb and libwayland). That includes the libraries of Qt’s X11 plugin (libxcb-cursor, libxkbcommon-x11 and a few more), so the build machine must have them installed: the workflow does, and the build script fails if the X11 plugin of the finished folder cannot find any of them. If a build misbehaves on another distribution, check which libraries it loads, and exclude the offender in packaging/alto.spec.

To try a build without touching your own install, extract it and run ./alto/alto, or run install.sh with ALTO_PREFIX, XDG_DATA_HOME and XDG_CONFIG_HOME pointing at scratch folders.

Building the Windows installer, and the release workflow

scripts\build-windows.ps1 builds dist\alto-<version>-windows-x64-setup.exe. It needs Windows, uv, Python 3.13 and Inno Setup 6. Like the Linux script it freezes Alto with packaging/alto.spec and checks that the program starts; then it compiles packaging/windows/alto.iss and tries the installer for real: a silent install, a run, a silent uninstall that must keep the data, and an uninstall with /PURGE=1 that must remove it. That test uses the real %APPDATA%\Alto, so run it only on a computer where that folder may be touched, such as a CI runner. The installer is for one user (no administrator prompt); its AppId in alto.iss must never change, because a newer installer finds the copy it updates by it. The uninstaller asks whether to also remove the practice history (%APPDATA%\Alto) and the settings (HKEY_CURRENT_USER\Software\alto); a silent uninstall keeps them unless it is given /PURGE=1. Local builds and pull request builds produce an unsigned installer.

Microsoft’s Visual C++ runtime comes from Windows, not from the installer. packaging/alto.spec leaves out the copies that Python, Qt and Shiboken bring, fails the build if one remains, and records which runtime files the program needs and the newest version among them. The installer checks that Windows has them, at least that new, and otherwise downloads Microsoft’s Visual C++ Redistributable, checks Microsoft’s signature on it and runs it, both in an ordinary install and in the silent install of an update. The build test runs that step once with /RUNTIMETEST=1, so it needs the internet. Alto does not use NumPy, which is only a test dependency.

Windows installer signing

To build a signed candidate, run Release manually on main. Download the windows-signed artifact and compare its SHA-256 with the signing job summary. On Windows, open Properties → Digital Signatures on the downloaded installer and inspect the publisher and timestamp. The windows artifact contains the unsigned build used as input.

The signing job uses the windows-signing GitHub environment. Its federated credential authenticates the job to Azure with AZURE_CLIENT_ID, AZURE_TENANT_ID, and AZURE_SUBSCRIPTION_ID. The environment variables AZURE_SIGNING_ENDPOINT, AZURE_SIGNING_ACCOUNT_NAME, and AZURE_CERTIFICATE_PROFILE_NAME select the signing profile. The candidate job includes that signed installer in the release checksums.

Signing releases, once

A packaged copy of Alto updates itself, and it installs only what is signed with a key that came with it. The key pair is made once:

  1. Run python scripts/make_signing_key.py. It prints a private key and a public key and writes nothing.

  2. Store the private key as the GitHub secret ALTO_SIGNING_KEY (the repository’s Settings → Secrets and variables → Actions), and keep an offline copy of it, for example in a password manager. Whoever has it can sign an update that every copy of Alto will install, and if it is lost no copy can be updated by a release signed with a new key: people would install the next version by hand.

  3. Put the public key in UPDATE_PUBLIC_KEYS in alto/updates.py and commit it. Until it is there a packaged copy does not replace itself; it is only told that a newer release exists, and the Release workflow refuses to publish.

The Release workflow signs SHA256SUMS with the secret (scripts/sign_release.py) and uploads SHA256SUMS.sig with it. Before it builds anything it signs a probe file, and the script checks the signature against the public key in the code, so a secret that is not that key’s stops the release at once and not after the builds. UPDATE_PUBLIC_KEYS is a tuple so that a release can carry a second key before the first is retired.

alto --self-test checks, with no network, that a packaged build has what an update needs (the certificate authorities, which the bundled Python cannot count on the system for, and the signature check). Both build scripts run it. The Windows script also runs a newer installer over a running Alto with the arguments Alto uses, and checks that the old one closed, the new one was installed and Alto opened again. What cannot be tested before a release exists is a copy checking a real release, which first happens when a release newer than the installed one is published; try the update on a real Linux and a real Windows machine then.

Release workflows

  • Build packages builds and tests the Linux download and Windows installer. All desktop runners use the CPython patch in packaging/python-version and the wheel versions in uv.lock. Update the lock with uv lock when changing dependencies. The separate Tests workflow resolves the newest allowed versions with pip.

  • Package also builds the Apple Silicon test ZIP on packaging pull requests. The candidate workflow calls it to sign and notarize the Mac disk image.

  • Release builds the candidate on manual dispatch from main. A version tag promotes the reviewed downloads and matching sources to a normal GitHub release using the pre-release checklist.

Reporting problems

Open an issue on GitHub. Say which operating system and Python version you use, and which exercise you were in.

Adding a notation excerpt

Choose a passage whose music and source edition are in the public domain. For a modern transcription, verify the transcriber’s public-domain dedication as well. Record the precise source file URL, its SHA-256 digest, the historical edition, the part, and the measure numbers in excerpt.json. Add the edition to THIRD_PARTY_NOTICES.md.

Store the extracted score.musicxml and its engraved score.svg beside the manifest under alto/assets/excerpts/<work>-m<first-measure>-v<version>/. Preserve the prevailing clefs, key, and meter. Give each independently selectable component a group ID such as mark-0, and put its Alto notation term at the corresponding index in the manifest’s targets list. Mark every visible instance of a term that can be asked. Keep neighboring symbols as musical context. Tintable shapes inherit their group’s fill or use currentColor for strokes.

Run QT_QPA_PLATFORM=offscreen .venv/bin/python scripts/excerpt_hit_map.py <excerpt-directory> to generate hits.png from the engraved ink. Inspect both answer modes at narrow and wide sizes. Published IDs identify saved questions. Give corrected music or a changed marker order a new version and keep the original directory so older answers can still be opened.
